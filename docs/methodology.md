# 方法论：从电流波形到每日预算

这篇文档只讲一件事：**怎么得到一组自己敢信、别人能复现的功耗数字。**

---

## 1. 先定义问题

续航 = 电池可用容量 ÷ 平均电流。

对 10–30 mAh 的设备，"平均电流"的量级是 **0.1–1 mA**。
在这个量级上，下面这些东西都会显著改变结论：

- PPK2 的量程与采样率
- 测点位置（电池端 vs PMIC 输出）
- 平均窗口的选取
- 电池内阻造成的压降（低 SOC 时）
- 温度与老化

所以第一步不是优化，是**把测量条件写死并记录**。

## 2. 测量设置（PPK2）

必须记录在案的最小集合：

| 项 | 取值 | 为什么重要 |
|---|---|---|
| 采样率 | 1–10 kHz（看瞬态） | 低于 1 kHz 会漏掉毫秒级脉冲 |
| 量程 | 自动 vs 固定 | 量程切换本身会产生读数台阶 |
| 供电方式 | 电池端 / 电源模拟 | 内阻、压降、PMIC 行为完全不同 |
| 平均窗口 | 明确到秒 | "平均电流"没有窗口就没有意义 |
| 环境温度 | 记录 | 电池与 LDO 特性随温度变化 |

**常见陷阱**

1. **把峰值当平均**：马达、PPG LED、射频的瞬时电流很高，但对续航的贡献要按电荷（µA·s）算。
2. **量程自动切换**：低电流段的读数可能被量化误差主导，结论要留余量。
3. **用电源供电测电池续航**：电源没有内阻，低 SOC 时的掉电行为测不出来。
4. **只看一段波形**：周期很长的状态（如 30 分钟一次的自动测量）必须跑够多个周期。
5. **忘记电池容量口径**：额定 mAh ≠ 可用 mAh（截止电压、放电倍率都会影响）。

## 3. 切分：把波形对齐到状态

两种办法，建议都用：

- **GPIO 打点**：在状态进入/退出时翻转一个空闲 GPIO，PPK2 同步抓 —— 最准，需要板子留测试点。
- **日志时间线**：用 RTT/串口日志的时间戳切分 —— 方便，但有日志缓冲延迟，误差几十毫秒到几百毫秒。

切完之后，每个状态得到一组 `(平均电流, 每日时长)`。

**关键约束：状态必须互斥。**
如果"睡眠窗口"和"BLE 连接"会同时发生，就不要把两者简单相加。
两种处理方式：

- **状态机式**：定义互斥的复合状态（`awake_connected`、`awake_idle`、`sleep_window`…）；
- **基准 + 增量式**：先测最低功耗基线，再逐项叠加某一功能的增量电流。

`tools/power_budget.py` 采用状态机式。

## 4. 记账：预算模型

```
mAh/天 = Σ (电流_mA × 秒/天) / 3600
续航(天) = 电池_mAh / mAh/天
允许平均电流(µA) = 电池_mAh × 1000 / (目标天数 × 24)
```

示例：21 mAh、目标 5 天 → 允许 175 µA；目标 3 天 → 允许 292 µA。

**敏感度分析**比总账更有用：把某一项减半/去掉，续航变化多少？
这直接告诉你"下一个优化该做哪"。

## 5. 从数字到取舍

账算完，结论通常只有三类：

1. **某一项占了 50% 以上** → 先动它；
2. **分布很均匀** → 说明要靠架构改动（采样档位合并、唤醒策略），不是抠单点；
3. **待机就吃光预算** → 软件优化空间有限，需要产品/硬件层决策。

把 1/2/3 写清楚，比给一堆优化建议有价值。

## 6. 复现要求

任何写进案例的数字，必须能回答：

- 在哪块板子上测的？
- 固件版本 / 配置是什么？
- PPK2 的采样率与量程？
- 平均窗口多长、跑了几个周期？
- 电池什么型号、什么 SOC？

缺任何一项，这个数字就只能当参考，不能当结论。
