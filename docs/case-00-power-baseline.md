# 案例 00 · 给设备建一张"状态电流基线"，然后抓回归

> **数据说明**：本文数字为**示例（illustrative）**，来自虚构设备的占空比模型，不是任何真实产品数据。
> 方法可直接套用：先建基线，再对比版本，找异常。

## 1. 为什么需要基线

功耗问题最难的从来不是"测一次电流"，而是：

- 这个数**正常吗**？
- 改了代码之后，**变差了吗**？
- 哪一段**变差的**？

三个问题都靠"基线表"回答。没有基线，每次都是重新猜。

## 2. 基线表长什么样

按**状态**（不是按模块）列，因为电流是按状态花的：

| 状态 | 规格 | v1 | v2 | v3 | v4 |
|---|---|---|---|---|---|
| 待机（不佩戴） | < 70 µA | 121 | 77 | 78 | **83** |
| 待机（佩戴） | < 70 µA | 122 | 88 | 87 | **89** |
| 船运模式 | < 1 µA | 0.07 | 0.05 | 0.10 | 0.05 |
| 蓝牙连接 | < 50 µA | 172 | 83 | 80 | **110** |
| 蓝牙广播 | < 70 µA | 121 | 87 | 80 | 103 |
| 心率采集（1 min） | — | 247 | 170 | 288 | 262 |
| 血氧采集（1 min） | < 300 µA | 473 | 447 | 876 | 457 |
| 马达（平均） | ≤ 50 mA | — | — | 45 | 26 |

单位：µA（马达为 mA）。同一列 = 同一固件版本。

## 3. 一眼看出的两件事

**第一，待机一直贴着规格线。** 77–89 µA，规格 < 70 µA——从 v2 起就没真正达标。

**第二，蓝牙连接在 v3→v4 之间涨了 30 µA。** 80 → 110 µA，而同期其他状态变化很小。
这种"单点跳变"就是回归信号，应该去查 v3 到 v4 之间跟蓝牙相关的改动。

**这就是基线表的价值：它把"感觉续航变短了"变成"v4 的连接态涨了 30 µA"。**

## 4. 测量方法（可复现）

1. **测点**：电池端（最接近真实使用），不是 PMIC 输出；
2. **采样率**：1–10 kHz（要看得到 BLE 事件和传感器脉冲）；
3. **同步**：固件在状态切换时翻转一个 GPIO，或用日志时间戳对齐；
4. **切分**：按状态把波形切开，每段求平均；
5. **记账**：`mAh/天 = 平均电流(mA) × 时长(h)`；
6. **对比**：同一状态跨版本比较，差值 > 10% 就追。

## 5. 常见的坑

| 坑 | 后果 |
|---|---|
| 用自动量程 | 低电流段读数出现台阶，差几到几十 µA |
| 平均窗口太短 | 漏掉长周期事件（如 30 分钟一次的自动测量） |
| 测点选在 PMIC 输出 | 看不到 PMIC 自身静态电流 |
| 用电源代替电池 | 没有内阻，低电量行为测不出来 |
| 只看整机平均 | 无法归因到状态，改完不知道有没有用 |

## 6. 小工具

```bash
python tools/power_budget.py examples/power_baseline.example.json
```

把状态电流和占空比填进去，就能算每日电荷和续航；改一个状态，能直接看到续航变化。

## 7. 结论

**先有基线，再谈优化。** 基线表是功耗工作的"版本管理"：它让回归可见，让取舍有据。
